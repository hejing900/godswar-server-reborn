# 参考服的任务模型：NPC 任务表与前置关系（2026-10-06 分析）

目标：把「只有一条主线、只能显示 1 条可接任务」补全成参考服那样「所有任务、按各自前置逐步开放」。
本文只写**从抓包与客户端数据里核对出来的结构**，以及「还缺什么才能补全」。未验证的部分明确标注。

## 1. 参考服的模型（已证实）

模型分两半：**静态的 NPC 任务表** + **动态的 available 标志**。

### 1.1 静态：每个 NPC 一张固定的有序任务表

证据全部来自库里的 S2C `10077` 抓包（`+4` npc、`+8` 条数、之后每条 `(quest u32, available u32)`）：

| 观测 | 数值 |
| --- | --- |
| 10077 帧总数 | 1894 |
| 不同 NPC | 99 |
| 不同任务 | 353 |
| **同一 NPC 的表随时间发生变化** | **0 次** |

最后一行是关键：同一个 NPC 在 09-22 到 10-06 之间反复被抓，表里的任务**一个不多一个不少、顺序也不变**。

表与角色无关的硬证据 —— NPC `5103` 的表：

```
519 (Lv2)  522 (Lv5)  524 (Lv7)  104 (Lv80)  105 (Lv90)  106 (Lv100)
```

抓到时角色是**2 级的斯巴达新号**。表里照样带着 Lv80/90/100 的任务，说明这张表是
「这个 NPC 会发的全部任务」，跟角色等级、进度都无关。

### 1.2 静态表可以怎么得到：`Quest.xml` 的 `GiverName`

对 88 张有任务的抓包表做交叉核对：

| 检查 | 结果 |
| --- | --- |
| 表内任务只对应**一个** `GiverName` | 87 / 88 |
| 表内任务是该 `GiverName` 任务集的**子集** | 87 / 87 |
| 表内有该名字任务集之外的任务 | 1 张（多出 1 条：1630） |

所以规则是：**`表(npc) = { 任务 : GiverName(任务) == 该 npc }`，再减去少量被服务端剔除的行。**

被剔除的部分不需要猜，抓包直接给了：某张表相对它的 `GiverName` 任务集**少掉的**共 180 条，
其中 162 条是**等级区间废行**（`MinLevel > MaxLevel`，或 `200/200` 占位行）。
剩下 18 条等级正常却仍被剔除（如 300 Lv67-80、1163 Lv76-90、1300 Lv67-80，以及一批 Thebes 130-140 的任务），
另有 52 条废行**反而被列进了表**（1574~1626 一段）。这 18 + 52 = 70 条是**有抓包依据的例外清单**，
可以直接查表修正，不需要发明规则。

### 1.3 动态：`available` 标志 = 该 NPC 的「链首」

同一个 NPC 的表不变，但标志位随进度**在表内前移**（库里的标志历史）：

| NPC | 表 | 观察到的标志 |
| --- | --- | --- |
| 5286 | 1531,1532,1533,1534 | 1531 → 1532 → 1533 → 1534 |
| 5282 | 1537,1538,1539 | 1537 → 1538 → 1539 |
| 5195 | 1520,1521,1525,1527,1528,1529 | 1525 → 1527 → 1528 → 1529 |
| 5200 | 1292,1293,…,1645 | 1292 → 1293 |
| 5103 | 519,522,524,104,105,106 | 519 → 519 → 522 → 524 |
| 5054 | 520,521,525,527,528,529 | 520 → 520 → 521 |

**一个 NPC 可以同时有多个链首**，说明他身上挂着好几条互不相干的链：

```
npc 5176  表 = 1207 1208 1209 1223 1224 1225 1226 1210 1211 1212 1227 1228 1229 1230 1369 1370 1389
  17:47      {1208, 1210}
  09-24~09-28{1208, 1211} → {1209, 1211}
  10-04      {1223, 1212, 1389}
```

`1208` 与 `1210` 同时亮，说明 `1207→1208→1209` 是一条链、`1210→1211→1212` 是另一条链；
批量后移到 `{1223,1212,1389}` 说明还有第三、第四条。**表里的顺序就是链的顺序（逐条拼接）**，
这也是为什么表的顺序不是任务 ID 顺序（5103 的表是 519,522,524,104,105,106 而不是 104,105,106,519,522,524）。

### 1.4 `10092` = 全服 NPC 标志位的并集

本会话里，附近 14 个 NPC 的 10077 一共点亮了 7 个任务：

```
1142, 1146, 1172, 1232, 1235, 1275, 1293
```

**这 7 个全部出现在 10092 的 19 条名单里**（反向为空）。
剩下 12 条属于没推送 10077 的远处 NPC（Parnitha_1_001/005/018/020、Athens_Newbie_006、Marathon_All_009 …）。

结论：`10092` = 遍历**所有** NPC，取其表里 `available=1` 的任务，做成并集。

## 2. 现状与差距

| 项 | 现状 | 参考服 |
| --- | --- | --- |
| 任务总数 | `StarterQuestChain` 920 行 | `Quest.xml` 1176 条，197 个发放 NPC，1174 条有 `GiverName` |
| 结构 | **一条线**（每阵营一个根）→ 前沿恒 1 | 每个 NPC 数条链，各自一条前沿 |
| 可接任务 | 1 条 | 同角色实测 19 条 |
| 路由 | `10077/10078/10080/10092` 已能发 | — |
| `available` 计算 | 按「列表位置」 | 按**每个 NPC 每条链的首个未完成** |

**只把门禁从「列表位置」改成「按 NPC 分链」是不够的**：我们那条线本身是生成器排出来的，
即使换判法，斯巴达也只有 2 个根（518 和一个 `QuestId=0` 的异常行）、雅典 1 个根，还是给不出 19 条。

## 3. 还缺什么

补全需要两样东西，难度完全不同：

### 3.1 任务表（可做，有依据）

- 从 `Quest.xml` 的 `GiverName` 生成 `npc → [任务]`，覆盖 197 个 NPC、约 1174 条任务；
- 剔除等级废行（`MinLength > MaxLength` 或 `200/200`）；
- 再按抓包得到的 70 条例外清单修正。

产出即可用来重做 `10077`（NPC 对话里的任务菜单）与 `10080`，数据量大但**全部有据可查**。

### 3.2 前置关系（**这是真正的缺口**）

客户端数据里**没有**任何前置字段：

| 查过的位置 | 结论 |
| --- | --- |
| `Settings/Sys/Quest.xml` | 只有 ID/等级/阵营/发放者/位置，无前置、无 next |
| `Text/Quest/{id}.dat` | Title / Details / Objectives / Append / EndText，无 next |
| `Text/Quest*.dat`（Quest/QuestItem/QuestMonster/QuestRegion） | 只有名字与区域，无链路 |
| 客户端 Lua（`Localization/**`） | 没有引用 `QuestFind`(361003)，查找面板在 exe 内部 |
| 参考服目录 | 没有服务端任务表；`Settings/Sys` 就是上面那些 |
| 参考服日志 `Log/SYS *.log` | 只有 `GetQuestItem()WStringNull:0` 一类告警，看不出数据源 |

我们能观测到的只有 **45 个任务曾被点亮过标志**（1894 条表里）。要重建整张图，只能靠观测，有三条路：

| 路线 | 做法 | 能拿到什么 | 代价 |
| --- | --- | --- | --- |
| **A 挖已有抓包** | 把 1894 条标志历史与接受/交付事件（10081/10084/10090）按时间对齐，推 `X→Y` | 只覆盖已观测的 45 个任务 | 低，纯离线 |
| **B 定向抓包（推荐）** | 在参考服上针对某个 NPC：接掉当前亮的那条 → 重新拉该 NPC 的表 → 看哪条新亮 = 后继；逐个走完 | 该 NPC 每条链的**完整顺序**，逐个 NPC 累积 | 中，需要人工在参考服按脚本操作 |
| **C 找服务端原始表** | 继续找 `gworiginsv.exe` 的任务定义（内嵌或外部文件） | 一次到位 | 未知，目前没线索 |

## 4. 建议的推进顺序

> 补充（同日）：本文第 2 节里「NPC 发放的任务只差 4 条」那部分已经做完 ——
> 那 4 条卡的 `Peloponnese_All_006` / `Marathon_All_006` 已发布，
> 见 [quest-actor-port-20261006.md](quest-actor-port-20261006.md)。前置关系（第 3.2 节）仍未动。

1. **先做表**：`Quest.xml` + 例外清单生成 `npc → [任务]`，用它替换现在按线性链拼的
   `10077/10080`。这一步不看前置关系也能做，且立刻让「NPC 的任务菜单」变正确。
2. **再补前置**：走路线 B。每完成一个 NPC 的定向抓包，就把它的链写进数据表；
   门禁从「全局列表位置」换成「该 NPC 该链的首个未完成」。
3. **最后打开**：`AcceptableQuestIds` 已经写成「遍历全阵营取通过门禁的行」，
   链数据一旦变成多链，`10092` 会自动变成多条，不需要再改协议代码。

在拿到前置关系之前，**不建议**先把 1174 条任务全塞进可接名单——
那会让面板列出服务端其实还不该发、点了也接不到的任务。
