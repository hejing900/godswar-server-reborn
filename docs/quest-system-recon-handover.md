# 任务系统侦察结论（交接文档）

> 生成时间：2026-09-13
> 目的：把"实现任务系统"这件事的所有前期侦察成果固化下来，供新会话直接接续开发。
> 数据来源：真实抓包（`packet_transactions` 表 + `captures/godswar-proxy.log`）

---

## 一、核心结论（先看这个）

**任务系统由服务端权威管理，且协议已完全摸清，可以动手实现。**

最关键的一条发现：

> `10082` 那个 648 字节的包里，客户端发来的内容**全是本地内存指针**（每次都是同一个值 `0x001af634`），
> **服务端完全忽略它**，只把它当作"玩家触发了任务动作"的信号，然后用自己的权威状态回填 3 个包。

所以服务端实现时**不需要解析那 648 字节**，只需要：

1. 从自己的状态查出"这次交互对应哪个 NPC、哪个任务"
2. 回 `10082`（+4=NPC_ID，+8=QUEST_ID，+12=递增序号，其余清零）
3. 回 `10092`（48 字节；+4=可接任务条数，+8 起每条 2 字节，见下方订正）
4. 回 `10084`（+4=QUEST_ID，+8=递增序号）

## 二、任务协议族（实测确认）

### 2.1 opcode 总览

| opcode | 方向 | 长度 | 作用 |
| --- | --- | --- | --- |
| `10083` | C2S | 20 | 客户端任务请求（+8 = questId） |
| `10083` | S2C | 17 | 服务端回应 |
| `10082` | C2S | 648 | **接取/任务动作请求**（内容为客户端指针，服务端忽略） |
| `10082` | S2C | 648 | 服务端回写（+4=NPC，+8=任务，+12=序号） |
| `10091` | C2S | 8 | 两种用途（+4 区分）：`0x00810EFB` = 接取动作的配对确认；`16`/`4` = 任务窗口「查找」按钮 |
| `10092` | S2C | 48 | 当前角色**可接任务表**（+4=条数 u32，+8 起 20 个 u16 任务 ID）。**不是全零、不是常量** —— 见 [quest-lookup-panel-20261006.md](quest-lookup-panel-20261006.md) |
| `10084` | S2C | 12 或 16 | **任务确认**（+4=任务ID，+8=序号） |
| `10090` | S2C | 2048 | 任务快照（+4=记录数，+8=序号，+12=NPC，+16=任务） |
| `10077` | S2C | 20 | NPC 功能菜单（+4=NPC，+8=子ID，+12=序号） |

### 2.2 重要否证

- **`10069`（NpcFunctionAction）全程没有出现** → 任务**不走** NPC 动作通道。
  早期假设"任务接取走 10069"是**错的**，不要再沿这条路查。
- `10117` 在点击 NPC 时出现，但它是 **ForgeCancel**（4 字节），只是对话关闭的普通取消包，**与任务无关**。

### 2.3 实测样本（黄金对照数据）

**第 1 次接取任务**（17:00:06）：

```
661  C2S  10082  648  34f61a00ffffffff06020000...   ← +4=指针 +8=-1   +12=518
662  C2S  10091    8  fb0e8100                       ← 配对确认（+4=0x00810EFB）
664  S2C  10082  648  e3130000ef13000006020000...   ← +4=5091 +8=5103 +12=518
665  S2C  10092   48  0000...                        ← 条数 0：此刻没有可接任务
666  S2C  10084   12  ef13000006020000               ← +4=5103 +8=518
```

**第 2 次接取任务**（17:02:38）：

```
1370 C2S  10082  648  34f61a00ffffffff07020000...   ← +4=同一个指针 +12=519（递增）
1371 C2S  10091    8  fb0e8100
1373 S2C  10082  648  ef130000be13000007020000...   ← +4=5103 +8=5054 +12=519
1374 S2C  10092   48  0000...                        ← 条数 0
1375 S2C  10084   12  be13000007020000               ← +4=5054 +8=519
```

> 注意两次 `+4` / `+8` 的语义**互换了**（第1次 +4=5091、第2次 +4=5103），
> 实现前需再抓 1~2 条样本确认哪个字段是 NPC、哪个是任务 ID。

**点击 NPC（不含接取）时的包**（16:58:55、16:59:56）：

```
C2S 10067 (48B) → S2C 10067 (48B) → C2S 10068 (8B) → C2S 10117 (4B)
```

与接取动作对比即可区分：**点"接受任务"会出现 `10082` + `10091`。**
但反过来不成立 —— 任务窗口的「查找」按钮也发 `10091`，却不带 `10082`。
两者只差 `+4`：`0x00810EFB` 是接取配对，`16`/`4` 是查找。
本节两条接取样本的 `10092` 之所以全零，是因为此刻没有可接任务，**不代表 `10092` 恒为零**；
完整的可选任务表见 [quest-lookup-panel-20261006.md](quest-lookup-panel-20261006.md)。

## 四、协议字段结构

```
10084 (12/16 字节)  —— 最干净，优先实现
  +0  u16 declared_length
  +2  u16 opcode = 10084
  +4  u32 questId
  +8  u32 序号

10090 (2048 字节)  —— 任务快照
  +0  u16 declared_length = 2048
  +2  u16 opcode = 10090
  +4  u32 记录数
  +8  u32 序号
  +12 u32 相关NPC
  +16 u32 相关任务
  +20.. 其余记录（未接任务时全 0）

10082 (648 字节)
  +4  u32 (C2S=客户端指针 / S2C=NPC 或任务 ID)
  +8  u32 (C2S=-1       / S2C=任务 或 NPC ID)
  +12 u32 序号
  +16.. 其余（S2C 侧基本清零）
```

## 五、已确认与任务无关的东西（省得再查）

- **客户端二进制里的任务消息名表**（`.rdata`，文件偏移即 VA 约定）：
  `0x555EF0` 起有 `MSG_NPC_QUEST`、`MSG_NPC_QUESTVIEW`、`MSG_NPC_ACCEPTQUEST`、
  `MSG_NPCCANCELQUEST`、`MSG_NPC_COMPLETEQUEST`、`MSG_NPC_INCOMPLETEQUEST`、
  `MSG_NPC_QUESTFAILD`、`MSG_NPCREWARDQUEST`、`MSG_NPC_QUESTEXPLORERRESULT`、
  `MSG_NPC_QUESTKILLORCAST`、`MSG_NPC_QUESTGIVEITEM`、`MSG_PLAYER_ACCEPTQUESTS`
  —— **这些是"服务端→客户端"的消息名，不是客户端请求**。
- 客户端任务引擎的 **9 种动作类型**（数据表在 `0x560E48`，状态机在 VA `0x6C0F00`）：
  `1 KillMonster`、`2 Active_intValue`、`3 Active_UpperLimit`、`4 Active_LowerLimit`、
  `5 CancelQuest`、`6 Complete_Type`、`7 Button_Click`、`8 AcceptQuest`、`9 CompleteQuest`
- `MSG_PLAYER_ACCEPTQUESTS` 的处理代码在客户端 VA `0x4E1397`（读任务ID→解析→更新 QuestView）。

## 十一、2026-09-13 第二轮抓包：交任务流程与新发现

来源：`packet_transactions`（2.8 MB 原始日志）。这次抓到了**接取 → 交付 → 接续**的完整链路。

### 11.1 关键更正：`10082` 的 `+4` / `+8` 语义

第一轮曾怀疑这两个字段"在样本间互换"。**第二轮两个方向都抓到了，语义确定：**

| 方向 | 长度 | `+4` | `+8` | `+12` |
| --- | ---: | --- | --- | --- |
| C2S | 648 | **本地内存指针**（每次都是 `0x1AF634`） | `0xFFFFFFFF` | 序号 |
| S2C | 648 | **当前 NPC ID** | **任务 ID** | 同一序号 |

实测三组样本：

```
17:00:06  C2S 10082  +4=1766964(指针) +8=-1      +12=0x206
17:00:07  S2C 10082  +4=5091(NPC)     +8=5103    +12=0x206
17:02:38  C2S 10082  +4=1766964(指针) +8=-1      +12=0x207
17:02:38  S2C 10082  +4=5103(NPC)     +8=5054    +12=0x207
```

**所以服务端实现时：`+4` 填触发交互的 NPC，`+8` 填要处理的任务，`+12` 回显客户端的序号。**

### 11.2 交付/接续流程（新抓到）

以 `0x206 → 0x207` 这次交接为例（时间 17:02:33 ~ 17:02:39）：

```
1336  17:02:33  C2S  10084  16  +4=0     +8=0x206   ← 交付请求（+4 为 0）
1370  17:02:38  C2S  10082  648 +4=指针  +8=-1      +12=0x207 ← 向新 NPC 请求
1373  17:02:38  S2C  10082  648 +4=5103  +8=5054    +12=0x207 ← 新 NPC + 新任务
1375  17:02:39  S2C  10084  12  +4=5054  +8=0x207            ← 任务确认
```

**`10084` 两个方向语义不同，这是最容易踩的坑：**

- **C2S 10084（16 字节）** = **交付请求**，`+4` 为 `0`，`+8` 是**要交付的任务**（即上一个任务）
- **S2C 10084（12 字节）** = **接取确认**，`+4` 是**新接的任务**，`+8` 是序号

也就是说任务链是：`S2C 10084(5103)` 接取 → 客户端做事 → `C2S 10084(+4=0)` 交付 5103 →
向 NPC 5103 请求 → `S2C 10084(5054)` 接取 5054。

### 11.3 `10090` 任务快照的真实结构（新解析）

`10090` S2C 2048 字节，骨架：

| 偏移 | 含义 |
| ---: | --- |
| `+0` | 帧长（`0x0800`） |
| `+2` | opcode（`0x276A`） |
| `+4` | u32 **记录条数** |
| `+8` | u32 **序号**（与 `10082`/`10084` 同一序列） |
| `+12` | u32 NPC ID |
| `+16` | u32 任务 ID |
| `+20` 起 | 记录区 |

记录区不是定长数组，而是**一段固定大小的槽位区**，每个槽位带自己的 `0xFFFFFFFF` 哨兵和
`0x01010101` 标记。实测任务 5103 的槽位里有 4 条目标，每条 20 字节：

```
e8030000 01000000 50000000 28000000 83000000   ffffffff 01010101
   1000      1        80       40       131
78050000 01000000 50000000 3c000000 83000000   ffffffff 01010101
   1400      1        80       60       131
a4060000 15000000 5a000000 b4000000 83000000   ffffffff 01010101
   1700      21       90       180      131
08070000 15000000 5a000000 3c000000 83000000   ffffffff 01010101
   1800      21       90       60       131
```

字段推测：`+0` 目标类型/ID，`+4` 目标数量，`+8`/`+12` 当前/上限，`+16` 标记。
**这条需要再用"同一个任务、不同进度"的样本比对才能定死**，当前只有"已完成"（`+4=1` 或 `21`）的状态。

快照在任务状态变化后由服务端主动重发（实测 17:06:10、17:12:10 各重发一次，内容一致）。

### 11.4 `10083` 已定论

```
C2S 10083 20 字节  +8 = 1767200 (0x1AF4A0)
S2C 10083 17 字节  +4 = 5103    +8 = 1767200
```

`1767200` **不是任务 ID**（任务 ID 是 5103 这种量级）。它更像**地图/场景 ID**，
所以 `10083` 是"**查询该场景有哪些任务**"，服务端回其中一个任务 ID。
第一轮把它当任务列表查询是对的，但要修正为**按场景查询**。

### 11.5 第一轮那条 `10071` 的矛盾——已解决（且我当时的结论是错的）

第一轮我写"抓包实测头是 12 字节、服务端代码写 16 字节，两者不可能同时成立"。
**这个判断是错的。** 正确布局是 **16 字节头 + N×88 字节记录**，其中：

- `+12` 是 **u32 余额**（服务端出口改写的位置）
- 记录内 `+0` 是道具 ID、`+68` 是单价

之所以当时量出 `12 + N×88` 恰好整除，是因为**每帧最后一条记录比满步长少 4 字节**
（缺的是尾部数量字段）。权威依据是**已跑通的 B-GOLD 商店目录**：它同样是 `16 + N×88`，
`+12` 是余额。详见 `docs/point-exchanger-shop.md`。

**教训：拿"恰好整除"当证据是不可靠的；要用一份已经跑通的数据做对照。**

### 11.6 仍未解决：任务 ID 映射（这是当前最大的拦路石）

抓包里的任务 ID 是 `5103` / `5054` / `5102`，而客户端 `Settings/Sys/Quest.xml`
的任务 ID 范围是 **0 ~ 1656**（共 1176 条，与 `Text/Quest/*.dat` 的 1306 个文本文件同域）。

已排查并**排除**的可能性：

| 查过的东西 | 结果 |
| --- | --- |
| `Quest.xml` 里有没有 5103/5054/5102 | 没有 |
| `Text/Quest/5103.dat` 等同名文件 | 没有（文件编号只到 1656） |
| 全客户端搜 `5103` 的映射表 | 只命中道具/技能/怪物等无关文件 |
| `RookieQuestReward.xml` / `BeginnerConfig.xml` | 是奖励/新手配置，不含任务 ID 映射 |
| 线性偏移假设 | **不成立**：giver `Sparta_055` 对应客户端任务 55，但抓包里任务 ID 是 5054 |

还有一个容易混淆的点：抓包里的任务 ID 和 **NPC 交互 ID 是同一量级**
（`Sparta_104` 的交互 ID 恰好是 `5103`），所以**不要**看到 `+4=5103` 就以为是任务——
那一帧的 `+4` 是 NPC、`+8=5054` 才是任务。

**结论：服务端任务 ID 是服务端自己的编号体系，和客户端任务文本没有可推导的算术关系。**
下一步要么找到服务端侧的任务表，要么**让服务端直接使用客户端的任务 ID（0~1656）**——
后者看起来更省事，因为客户端文本就是按这套 ID 索引的，服务端没必要另起一套。

### 11.7 下一步（给接手的人）

已经可以动手，建议顺序：

1. **定 ID 方案**：直接用客户端任务 ID（0~1656），`Text/Quest/<id>.dat` 就是文案，
   `Quest.xml` 就是任务定义（给予者/回复者/坐标/等级/阵营）。这样零映射成本。
2. **协议层**（纯函数，可单测，零风险）：
   - 收 `C2S 10082` → 回 `S2C 10082`（`+4`=NPC、`+8`=任务、`+12`=回显序号）
   - 收到 `C2S 10091` → 回 `S2C 10092`：48 字节，`+4`=可接任务条数、`+8` 起 20 个 u16 任务 ID。
     接取配对（`+4=0x00810EFB`）与「查找」（`+4=16`/`4`）共用这一条应答；
     接取后本角色没有可接任务，条数自然是 0，与本节样本一致。
   - 回 `S2C 10084`（`+4`=任务、`+8`=序号）
   - 状态回复用 `S2C 10090` 快照（结构见 11.3）
3. **数据表**：任务定义走表，不要硬编码。
4. **交付**：注意 `C2S 10084`（16 字节，`+4=0`）是**交付请求**，语义和 S2C 的 `10084` 不同（见 11.2）。

### ⚠️ 额外发现：`10071` 商店目录的"头长度"与现有服务端代码矛盾

2026-09-13 17:06:39 抓到"副本积分兑换官"（NPC **5074** / `Sparta_077`）的 5 个 `10071` 目录包：

| frame | 总长 | `(长-12)/88` | `+10` 条数 | `+8` 分类头 |
| ---: | ---: | ---: | ---: | --- |
| 1 | 1420 | 16 ✅ | 16 | `00 04 10 01` |
| 2 | 100 | 1 ✅ | 1 | `00 04 01 00` |
| 3 | 1332 | 15 ✅ | 15 | `01 04 0f 01` |
| 4 | 1068 | 12 ✅ | 12 | `02 04 0c 01` |
| 5 | 980 | 11 ✅ | 11 | `03 04 0b 01` |

**5 个包全部满足 `总长 = 12 + 条目数 × 88`，且 `+10` 的条数与实际条数完全一致。**

但现有服务端代码 `PacketBuilder.CapitalNpcShops.cs:11` 用的是：

```csharp
private const int ShopCatalogHeaderBytes = 16;   // ← 抓包实测是 12
private const int ShopCatalogItemBytes = 88;
```

**两者不可能同时成立。** 按 16 字节头算，frame 2（100 字节）会得出 `100-16=84`，
不是 88 的整数倍 → 现有代码的 `InflateCatalog` 校验会判定帧非法并跳过。

头部字段（实测）：
```
+0  u16 长度
+2  u16 opcode = 10071
+4  u32 NPC 交互ID
+8  u8  分类序号（0,1,2,3…）
+9  u8  常量 0x04（疑为货币类型 = B-GOLD）
+10 u8  本帧条目数
+11 u8  0x01 / 0x00（新分类页标记，与现有代码注释一致）
+12 起 = N × 88 字节记录
```

> **注意：现有服务端用的 16 字节头可能来自更早、不同版本的抓包。**
> 后续做商店/兑换功能前，必须先用真实抓包重新确认头长度，
> 并核对 `PacketBuilder.CapturedCapitalNpcShops.cs` 里那 3 份硬编码目录是否仍然正确。
