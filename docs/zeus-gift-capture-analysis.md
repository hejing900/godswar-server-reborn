### 2.4 开窗请求与献礼确认的差别

开窗请求（所有槽位 `-1`）会带一个固定参数块，例如忠实信徒：

```
[7]=84819908 [8]=829100520 [9]=84819908 [10]=829100536
[11]=0 [12]=747775096 [13]=0 [14]=916008991 [15]=808859800
[16]=1767948 [17]=8458971
```

这些不是按钮号，含义未确认（**待实测**）。

献礼确认那一次（`01:02:40.525`）槽位是：

```
[0]=1001  [1]=0  [7]=18
```

即"上一次点了 1001，本次点了 `0`，参数块第 0 格是 `18`"。
`18` 的含义未确认（**待实测**）——它落在固定参数块里，不是点击槽。

### 2.5 ⚠ 页号（脚本里的 `Index`）规则：**不是**打包列表的位置

现有文档 [npc-function-dialog-mechanism.md:120-163](docs/npc-function-dialog-mechanism.md#L120-L163)
说"`Index` = 功能号在打包列表里的第几位"。**抓包证伪了这条**。

直接证据（宙斯，`list=[26]` 只有一项，`Index` 按该模型只能是 1）：

| 时刻 | 玩家点了 | 服务端回 | 这些号只存在于 `NpcFunZeus.lua` 的哪一页 |
| --- | --- | --- | --- |
| `01:02:07.602` | 开窗 | `[4200,1001,1002,1003,101009]` | 第 1 页（`:119`、`:71-85`、`:161`） |
| `01:02:09.650` | 槽 0 = `1002` | `[1512,1006,1008]` | **第 2 页**（`:287`、`:267`、`:277`） |
| `01:02:15.933` | 槽 0 = `1002`、槽 1 = `1006` | `[1313,10013]` | **第 3 页**（`:512`、`:516`） |

第二条应答画出了按钮 `1006`，玩家随后点的就是 `1006`（槽 1）。
`1006` 在 `NpcFunZeus.lua` 里只有第 2 页（`:267`）有分支 —— 所以**第 2 次应答确实是在第 2 页上渲染的**。
同理 `01:03:09.365` 回的 `[1513,1009,1007]` 画出 `1007`，玩家点 `1007` 后回 `[1014]`，
而 `1014` 只在第 3 页（`:535`）。

独立于宙斯的证据（`Athens_074` npc 5212，`list=[16,24,50]`，玩家这次用的是功能号 `24`）：

| 时刻 | 玩家点了 | 服务端回 | 落在 `NpcFunLostBook.lua` |
| --- | --- | --- | --- |
| `17:19:12.419` | 开窗 | `[101, 1, 2]` | **第 1 页**（`:15`、`:18`、`:24`） |
| `17:19:14.247` | 槽 0 = `1` | `[601]` | **第 2 页**（`:44`） |

功能号 `24` 在列表里是第 2 位；如果 `Index` 跟着列表位置走，第一条应答就会是第 2 页，
`101`/`1`/`2` 一个都画不出来 —— 可是玩家接着点了 `1`。所以 `Index` 与列表位置无关。

**结论**：客户端传给 Lua 的 `Index` = **本次开窗以来服务端发出的第几次 `10070`**（1、2、3……），
每次 `S2C 10067` 开窗归零。`Type` 是 `10069` 里那个功能号（客户端从打包列表里选的，
同一 NPC 的不同服务可以中途切换：npc 5212 实测用过 `16`、`50`、`24` 三个值）。

**一处反例，必须记下来**：`NpcFunWar.lua` 里有 4 段实例，第 4 次应答是 `[1755]`，
而 `1755` 只存在于该脚本的第 2 页（`:356`）和第 3 页（`:804`），第 4 页没有。
按上面的规则，这 4 次应答客户端画不出任何东西（玩家随后都重新点了 NPC）。
同一天另有 4 段结构完全相同的实例，第 4 次应答是 `[170001,114002,…]` 这种
只存在于第 4 页（`:1249`、`:1261`）的号，是能画的。
两种都算"第 4 次应答"却落在不同页，说明**参考服自己在这个分支上发错了页**，
或者页号规则在第 4 页之后还有别的因素。宙斯只用到第 1–3 页，不受影响，
但**给其它 NPC 做第 4、5 页时要以实测为准**。

### 2.6 其它同时确认的事实

- `10070` 的 +8 是原样回显，服务端不需要维护"当前页"状态。
- 一条应答里只放同一页的号；放了不在目标页上的号，客户端就不画（见 2.5 的反例）。
- `flags` 必须是 `0x200`，打包列表 1–999、不重复、≤3 项。

## 5. 实现方案

> **本节已按方案落地**，见 §0 的文件清单。落地时相对本节的修正：
> 页号不再靠"分步表隐式成立"，而是 `NpcDialogPages` 显式计数并在每次发应答前
> 断言目标页；圣徒的缴纳确认落在第 3 页、粉尘框确认落在第 5 页（本节原稿把
> 两步都记在第 2/4 页）；抽取要求物时直接用物品 id 当 `SubID`（见 §0）。

### 5.1 协议层（必须先改，否则内容层改了也走不动）

1. **点击取最新槽位**（`GameClientHandler.NpcDialog.cs:262-268`）：
   点击数组是 `+16` 起的 7 个 int32（槽 0–6，到 `+40` 为止），取其中
   **最后一个不等于 `-1`** 的值；7 个全是 `-1` 就是开窗请求。
   槽 7（`+44`）往后是开窗请求才填的固定参数块，不要当成点击。
   建议在 `PacketDecoding` 里加一个专门的读取器，把槽位数组和参数块都暴露出来，
   因为献礼确认还要看参数块（2.4）。

2. **页号显式化**：给每个 NPC 对话会话记一个应答序号（键：连接 + NPC 对象 id），
   `S2C 10067` 开窗时清零；每次发 `10070` 前取"当前序号 + 1"作为**目标页**，
   发完自增。handler 里对每一步做一次断言：**这一步要发的号必须写在该页的分支上**，
   不满足就打日志并且不发（宁可留空也不要发一个画不出来的号）。

3. **一步一次应答**：客户端的页号只认应答次数，所以服务端**每次 `10069` 最多回一次 `10070`**。
   现在 `HandleZeusGiftDialogueAsync` 是"表里没有就不回"（`:522-530`），
   这会让页号停在原地——后续每一步都会差一页，需要改成"没登记也要回一次可渲染的号"。

### 5.2 内容层：两个 NPC 的角色对调 + 忠实信徒的前三页

| 步骤 | 忠实信徒（`Athens_113`/`Sparta_113`） | 页 |
| --- | --- | --- |
| 开窗 | `[赠品要求, 1001, 1002, 1003, 进度号]` | 1 |
| 点 `1001` | `[1005]` | 2 |
| 点 `1002` | `[1512, 1006, 1008]` | 2 |
| 点 `1003` | `[1513, 1009, 1007]` | 2 |
| 点 `1006` | `[1313, 奖励级×10000+13]` | 3 |
| 点 `1007` | `[1014]` | 3 |
| 点 `1008` / `1009` | **未抓到**；参考服对 `1008` 没回应答 | 3 |

`1008`（"太黑了,再见!"）与 `1009`（"让我再考虑下吧"）在脚本里是第 2 页的按钮，
它们的应答会是第 3 次应答 → 第 3 页。第 3 页里语义合适的收尾分支是
`1108`（"你又懒又没水晶给我…回家打酱油去吧！"，带 `EndMessage`）和
`1102`／`1104`（带 `EndMessage`）。**这三个号都是从脚本读出来的，不是抓包实证，
必须在客户端里点一次确认。**

祈祷圣徒这一侧把现有的 `[1511,1200,1201,101]` → `[1203,1204,1205]` → …这套表接过去，
但**首屏文字用 `1511` 还是 `1514` 没有实证**（参考服那次是等级不足）。
现有分步表在"页号 = 应答序号"下基本自洽，可以直接沿用 —— 只有一处要改
（见下面的 `200..207`）：

```
页1 [1511,1200,1201,101]
  1200 → 页2 [1202]        1201 → 页2 [1203,1204,1205]     101 → 页2 [1517,200..207]
  1202 → 页3 [1206]        1203 → 页3 [1518,1207..1211]    1204 → 页3 [1516,4000..4006]
  1205 → 页3 [1611]        200..207 → 页3 ✗见下
  1207..1211 → 页4 [3000,3001]        302 → 页4 [1230..1236]     4000..4006 → 页4 [5102]
  1230..1236 → 页5 [3007]
```

（`3000/3001` 只在第 4 页（`NpcFunZeus.lua:668`、`:673`）、`1230..1236` 只在第 4 页（`:628`）、
`3007` 只在第 5 页（`:707`）—— 与"页号 = 应答序号"对得上。）

**唯一一处跨页错**：现有 `ZeusGiftLuckBracket` 是 `[3000,3001,302]`，
但 `3000`/`3001` 只存在于第 4 页，`302` 只存在于第 3 页（`:324`）。
点击 `200..207` 是第 3 次应答 → 第 3 页，所以那两个号客户端画不出来。
`ZeusGiftDustBracket`（点 `1207..1211`，第 4 次应答 → 第 4 页）用 `[3000,3001]` 才是对的。
第 3 页该回什么号**没有抓包**，需要按脚本选一个第 3 页上存在的号再实测。

### 5.3 事件状态层（抓包给不了，只能按官网规则设计）

官网（[zs.176.com/yxzl.php?yx_id=72](https://web.archive.org/web/20101201193209/http://zs.176.com/yxzl.php?yx_id=72)）
的规则，和抓包里看到的编码能对上：

| 规则 | 抓包里的对应 |
| --- | --- |
| 每天 10 次，周末 12 次 | `Z1401`-`Z1407` 文案；`1105`/`1106` 是"已缴纳 12/10 次"的收尾分支 |

| 幸运大比拼 1–1000 分 | 第 3 页 `mod(SubID,10000)==1/2/5/4`、`mod(SubID,1000)==901/902`（倒计时） |

需要落库的字段（建议按现有许愿池的做法：一个角色一行、行里带"所属自然日"，
跨天读出来就当没用过，见
[PostgresWishingPoolUsageStore.cs:27-35](src/Godswar.Server/Infrastructure/WishingPool/PostgresWishingPoolUsageStore.cs#L27-L35)）：

- 当日献礼次数、当前奖励级别、本轮要求的物品/装备（随机抽取）、是否已放弃过
- 当周缴纳的祈祷石数、当周可兑换次数（含全服总量对免费次数的影响）
- 幸运大比拼：本阵营、道具、分数、投分时间（比最高分，同分先投者胜）

**这部分没有任何抓包证据**，属于"按官网规则设计"，必须明确标注，
不要写成"实测"。
