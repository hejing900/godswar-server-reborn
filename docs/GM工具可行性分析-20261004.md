# GM 工具可行性分析：角色定位 · 刷怪 · NPC 对话 · 导出

> 需求：①按角色名搜索并读角色所在地图/坐标；②把当前地图+坐标存成多个命名标记点；
> ③在标记点上刷怪并设置血量/攻击等属性；④新增 NPC，支持多级窗口、每窗口配按钮与文本；⑤导出配置。
>
> 本文只做可行性判断，**未改任何代码**。每条结论都附文件名/行号或实测证据。

## 0. 结论速览

| # | 需求 | 能不能做 | 关键前提 / 约束 | 量 |
|---|---|---|---|---|
| ① | 按名字搜角色、读地图+坐标 | **已实现**，只差界面显示 | 库里的坐标是最近一次存档，最多滞后 ~2 秒 | 极小 |
| ② | 多个命名标记点 | **能** | 存一张 GM 表（不能存文件，容器读不到） | 小 |
| ③ | 点位刷怪 + 属性可设 | **能** | 服务端要加"运行时覆盖层"；新怪必须复用已抓到的模板包体 | 中 |
| ④ | 新增 NPC + 多级窗口 + 按钮 + 自由文本 | **能，但分两半** | 放置 NPC 没问题；**"自由文本 / 自定义名字"必须打一次客户端 Lua 补丁** | 中～大 |
| ⑤ | 导出 | **能** | 导出 = 服务器覆盖行 + 客户端补丁 + JSON | 小 |

一句话：**①②⑤ 是小活；③ 有现成方案设计（仓库里那份交接文档）；④ 是唯一要动客户端的一半，但不是"做不到"，而是"必须配补丁"。**

## ① 按角色名搜索 + 地图/坐标 —— 已经实现

**现状**：`tools\Godswar.GmTool\GmStore.cs:61-138` 的 `SearchCharactersAsync` 已经 select 了
`cb."Map"` / `cb."Pos_X"` / `cb."Pos_Z"`，并在返回 JSON 里给出 `map` / `positionX` / `positionZ`。
`tools\Godswar.GmTool\wwwroot\index.html` 的 `renderCharacter` 没把它们显示出来 —— 这是唯一的缺口。

**精度（必须如实告知操作者）**：

- 位置**每 2 秒**最多落库一次：`GameClientHandler.cs:27` `PositionPersistInterval = TimeSpan.FromSeconds(2)`，
  落库判断在 `GameClientHandler.PlayerVisibility.cs:506`。所以在线角色读到的坐标最多滞后 ~2 秒
  （奔跑时几米），离线角色是最后位置。
- **没有实时坐标接口**。服务端的 `9090` 管理端口是运维探针（就绪/排空），
  `src\Godswar.Server\Networking\RelayGateway\RelayGatewayMetrics.cs:8` 明确写着"不暴露管理端点"。
  要"零滞后"就得新增一个服务器接口，属于可选增强（P2）。

结论：**直接可用**；工具里同时提供"手动填坐标"输入框即可覆盖精度敏感的场景。

## ② 多个命名标记点 —— 能，且不需要动服务端

存一张 GM 表即可（工具直连同一个 PostgreSQL 读写）。**不能存成工具本地文件**：服务端跑在
`godswar-server` 容器里，读不到宿主机工具目录。

建议字段：`id / name / note / map_id / x / z / facing / created_at / updated_by`。
这张表同时是 ③④ 的输入（"在哪个点刷什么"）。

## ③ 点位刷怪 + 属性可设 —— 能，仓库里已经有完整方案设计

### 3.1 现状（已逐条核对）

| 事实 | 证据 |
|---|---|
| 刷新点来自**启动时 pin 的发布内容**，不是源表 | `PostgresWorldContentReaderLoader.Monsters.cs`；发布器注释"Runtime readers never consult the source tables" |
| `monster_spawn_definitions` **拒 UPDATE/DELETE**（不可变触发器） | 交接文档 §1.1；`trg_monster_spawn_definitions_immutable` |
| 包体 44 字节之后**未完全逆向**（外观/模型字节） | 交接文档 §1.2 |
| 物攻/魔攻/物防/魔防/命中/闪避/暴击目前是**代码公式** | `Game\MonsterCombatProfileCatalog.cs` 的 `Resolve` |
| 只有**暴击抗性**已经在库里可改 | `monster_combat_balance`（26 行），`Resolve` 里第 ③ 步 `profile with { ... }` |
| 等级 / 当前HP / 最大HP 是**每个刷新点一份**（包体 offset 12/20/24） | 交接文档 §1.2 |

### 3.2 做法：运行时覆盖表（交接文档的"方案 B"）

`docs\handover-20260927-monster-spawn-and-attributes-gm-config.md` 已经把这个方案写透（含要改的文件、
要避的 5 个坑）。核心是：**权威内容一字不动，另加一张 GM 表，在读取路径上按优先级叠加**。
仓库里已有两个同款先例（掉落 `monster_loot_rules`、任务奖励 `quest_reward_slots`），照抄即可。

4 种语义：改字段 / 加点（`source='gm'`）/ 屏蔽点（`enabled=false`，因为不可变表删不掉）/ 属性覆盖
（`NULL` = 不覆盖）。

### 3.3 生效时机：**怪物必须重启，NPC 不必**（我先前写反过一次，这里更正）

先说结论（都经代码核实）：

| | 改完什么时候生效 | 原因 |
|---|---|---|
| ③ 怪物 | **必须重启容器**（或显式重建该地图实例） | `MapInstance` 把怪物运行时**缓存到实例生命周期结束**：`MapInstance.MonsterInitialization.cs:26-49` `if (_monsterRuntime is not null) { ... return _monsterRuntime; }`，而默认地图实例是长期存活的。 |
| ④ NPC | **下次进图即生效**，不必重启 | `MapInstance.NpcCatalog.cs:10-45` 的 `PublishNpcDefinitions` 在集合**有差异时直接替换**实例目录（`changed` → 赋值 + 版本号 +1），而进图路径每次都重新构造 NPC 列表。 |

两者共同的读取点是 `GameClientHandler.LoginWorldEntry.cs`（`:410` 读 NPC、`:482` 读怪），确实**每次进图都执行**；
但 `PinnedWorldContentReader.ReadMapAsync`（`Application\World\PinnedWorldContentReader.cs:141-163`）是**纯内存**的
（从启动时建好的 `_maps` 字典克隆），它**不会再查库**。所以 GM 覆盖层必须是**另一次查询**，插在它之后：

```
mapContent = await _worldContent.ReadMapAsync(mapId)            // 启动时 pin 的权威内容（进程内不变）
mapContent = await gmOverrides.ApplyAsync(mapId, mapContent)    // ← GM 表在这里叠加
```

怪物那边**还有一个独立障碍**：`IWorldContentReader.cs:5-8` 明确写着这是
"one process-pinned, immutable projection ... must not switch revisions during the process lifetime"，
且 `MapInstance` 的怪物运行时缓存不会因为重新进图而重建 —— 所以 ③ 的改动要看到效果就得重启。

> 另外：仓库里现存的所有 GM 表（掉落、任务奖励、`monster_combat_balance`）**都是启动快照**，
> `monster_combat_balance` 的 DDL 注释里就写着"改完重启服务端"。③ 沿用这个约定即可。

### 3.4 硬约束

1. **新加的怪必须以某个已抓到的同类模板包体为底改字段**（offset 44 之后没逆向）。工具里应让操作者
   "选一个已发布的模板"，而不是从零造。
2. **迁移必须登记进 `PostgresSchemaMigrationCatalog.All`**，否则新表根本没建、读取器 select 报 42703 崩溃循环
   （交接文档 §3.2 记录了 2026-09-27 踩过）。**当前真实状态：迁移数 187，最后一条 id 是
   `20261003_226_zeus_gift_limited_stock_camp`** —— 交接文档写的"175 / `20260927_214_reward_item_attributes`"已经过期。
3. **`NULL` ≠ 0**：属性列一律用 `NULL` 表示"不覆盖"。
4. **属性语义要定死**：HP/等级是"每点一份"，属性是"每种怪一份"。工具必须明确"按模板批量展开"还是"逐点"，
   否则会出现"改了没反应"的困惑。
5. **没有现成的怪物对象 ID 分配器**（交接文档说"复用现有分配器"是错的）：现有几批自制怪各自用硬编码基数
   （温泉关 43000、斯巴达新手 44000、亚特兰蒂斯 42000、美杜莎 40000），GM 新增点必须自己分配。
   重复 ID 只在**首次进图**才炸（`MonsterMapRuntime.cs:78-92` 的 `ToDictionary` / `EcsMonsterMapRuntime.cs:82` 的 `_entities.Add`），
   所以工具必须先做唯一性预校验。
6. **属性覆盖必须放在优先级链的最末**：`MonsterCombatProfileCatalog.Resolve(CapturedMonsterSpawn)` 除了
   "代码写死覆盖 → 公式 → 库表暴抗"三步外，**还有第四步**——被动怪会被强制
   `PhysicalAttack = MagicAttack = 1`（`:166-168`）。GM 的攻击覆盖若插在它前面会被**静默清掉**。

## ④ 新增 NPC + 多级窗口 + 按钮 + 自由文本 —— 能，但要分清两半

### 4.1 服务端放置 NPC：**完全可行，我已经用同样的机制跑通过**

- NPC 的 `10020` 世界对象包是**服务端按 `NpcSpawnDefinition` 现场生成**的：
  `Packets\PacketBuilder.NpcDialog.cs:350` `WriteNpcWorldObjectAppearance` 只写
  地图+出场词（`ComposeNpcObjectType`）、对象 ID、x/y/z、朝向、模板键。**不需要抓包包体。**
- 实测证据：本次给 map 29 新增 7 个 NPC（`NpcContentBaselineV10`）后，线上日志
  `[npc] loaded map definitions character=test map=29 count=7` → `[world] ... npc-entered=7`，客户端正常显示。
- 注入点：`GameClientHandler.LoginWorldEntry.cs:410-445`（读图 → 兼容处理 → 捕获放置策略 → 过滤）之后加一层
  GM 附加/覆盖即可；那里**已经**做了"对象 ID 不能撞玩家/已占对象"和"坐标必须落在扇区内"的过滤
  （`:433` `WorldObjectIds.IsReservedForPlayer` + `WorldSectorVisibilityTracker.TryGetCell`）。
- 硬约束：**模板键必须是客户端已有的**（客户端按模板键查模型/外观数据）。所以只能"复用现成外观"，
  这跟③里"新怪要复用模板包体"是同一类约束。

### 4.2 多级窗口 + 按钮：**机制已查清，能表达**

客户端渲染规则（仓库自己的协议文档 `docs\NPC对话封包格式与应答读法-20260922.md` + 客户端 Lua）：

- 服务器 `10070` 的 `+12` 起是**一组号**，客户端**每个号画一行**；玩家点某行 → 客户端把那个号放回
  `10069` 的 `+20`，**页号（`10070` 的 `+8`）全程不变**。
- 客户端 `NpcFun.lua:176` `Set_NpcFun_Text(Type,Index,BtnID,SubID)` 按 `Type`（= 我们在 `10067` 里广播的
  功能号）分派到对应脚本，脚本里 `SubID == N` 的分支决定画什么。
- **多级跳转靠"换一组号"，不换页号**：点一个号 → 服务器回另一组号 → 客户端重画同一页。
  现有所有多级对话（传送员、许愿池、公会福利…）都是这个做法。
- 可点行上限 **12 个/页**：`D:\Godswar Origin\Localization\zh_cn\UI\XML\NpcFun.xml` 里只有
  `FirstWin_Button1`…`FirstWin_Button12`（外加确定/取消 `ButtonA1/A2/A3`）。`10070` 一包上限 20 个号
  （`PacketBuilder.NpcDialog.cs:330` 有 20 条校验），但超过 12 个可点号就没有窗口子控件可画了。
- 另有一条客户端约束：带 `EndMessage(true)` 的**结果号会关闭窗口**，**不能和按钮放在同一包**里发
  （协议文档第 41-42 行）。工具要把"结果页"和"菜单页"分开。
- 唯一未验证点：客户端脚本里存在 `Index == 2` 这类分支，说明参考服**可能**会中途改页号；
  但抓包里所有样本页号都保持不变，这条路径没有样本。**本方案不需要它**（多级靠换号实现），
  所以不构成风险；将来要用需单独做一次游戏内验证。

服务端这一半**很轻**：现有 `ScriptedNpcDialogue(FunctionNumber, OpeningMenu, Steps, PageSelections)`
（`Game\ScriptedNpcDialogueCatalog.cs:39`）已经能表达"多级 + 按钮"，只是目前**写死在代码里**。
只要把它改成从 GM 表读（数据驱动的对话树），④的多级窗口+按钮就成立，**完全不用碰客户端**。

### 4.3 "自由文本"：能做，但**必须打一次客户端补丁** —— 这是本次唯一的关键前提

为什么：对话框里每一行文字都由**客户端自己的 Lua** 决定，服务器只发"号"。
`NpcDescriptionDialogOpenAck` 的注释也写明"文本由客户端按脚本键自己解析，本包不带文本"。
`NpcFun.lua` 的分派函数签名是 `Set_NpcFun_Text(Type, Index, BtnID, SubID)`
（`Localization\en_us\UI\XML\NpcFun\NpcFun.lua:176`）——**四个参数全是整数，没有文本参数**；
而且它的分派链**没有 `else` 兜底**（全文 0 处 `^\s*else\s*$`），未知功能号就是什么都不画。

**先说三条容易踩的坑（都已核实）**：

1. **真正生效的是 `en_us` 那一份**。`Localization\zh_cn\UI\XML\NpcFunLoad.xml` 和
   `...\en_us\...\NpcFunLoad.xml` **两个文件里列的全是 `./Localization/en_us/...` 路径**。
   所以 `zh_cn\UI\XML\NpcFun\` 下那些同名 Lua **是死文件**，补丁必须打在
   `Localization\en_us\UI\Base\LuaText.lua`（无 BOM 的 UTF-8）。
2. **新增 Lua 文件不会自动加载**：`NpcFunLoad.xml` 是一张显式清单，新脚本要加一行
   `<Script File="./Localization/en_us/UI/XML/NpcFun/<新文件>.lua" />`。
3. `10067`/`10070` **一个字符串都塞不进去**：前者只带 `{npc, flags, 千进制号列表, 32字节 ASCII 脚本键}`，
   后者只带 `{npc, 页号, N 个 int32}`。

**好消息：客户端自带数据驱动建窗的工具，而且支持字面字符串。**

- `en_us\UI\XML\NpcFun\UIMAKER.lua` 提供 `UIMAKER:Create(win, 名字)`：只要定义一张全局表
  `UIList_<名字> = { {页号, 号, 类型, 文本, x, y}, ... }`（类型：`TEXT=1 / BUTTON=2 / INPUT*=3-5 / VALUE=6 / ENDTEXT=7`），
  它就自动生成该窗口的 `_SetUI` / `_SetText`。
- 关键一行：`FirstWin_Text1:SetText(WindowConf[4])` —— **`[4]` 既可以是 `LuaText` 的键，也可以是字面中文串**。
  也就是说"自由文本"不必去改 `LuaText.lua`，直接把文字写进表里就行。
- **它确实被加载**：`UIMAKER.lua` 与 `NpcFunFallback.lua` 都在 `NpcFunLoad.xml` 的清单里，
  且 `NpcFunFallback.lua` 正在用这套机制（`UIList_Fallback` + `UIMAKER:Create(win,'Fallback')`）。
- 编码没问题：目标文件 `en_us\UI\Base\LuaText.lua` 是**无 BOM 的 UTF-8**（355,236 字节，严格 UTF-8 校验通过），
  字面中文可以直接写。

**因此补丁内容很小、且可自动生成**：

1. 新增一个 Lua 文件（例如 `en_us\UI\XML\NpcFun\NpcFunGm.lua`）：一个 `UIList_Gm = {...}` + 一行
   `UIMAKER:Create(win,'Gm')`；
2. 在 `NpcFunLoad.xml` 里加一行加载它；
3. 在 `en_us\...\NpcFun\NpcFun.lua` 的两处分派里各加一条
   `elseif Type == <GM功能号> then NpcFunGm_SetText/SetUI(...)`；
4. 可选：往 `en_us\Text\NpcName.dat` / `NPCDescription.dat` 追加行，给 GM NPC 自定义**名字**和**描述**。

**名字/描述也在客户端**（本次实测确认）：`Localization\zh_cn\Text\NpcName.dat` 是
`NPC键<TAB>名字`（例如 `Athens_072 → 活动运输员`、`Execrativelys3_001 → 活动传送者（55级）`），
`NPCDescription.dat` 同理（UTF-16LE）。注意 `NpcFunLoad.xml` 只把 **Lua** 指向 en_us，
`Text\NpcName.dat` 是分语言的，要按客户端当前 `Locals=zh_cn` 打对应那份。

**仓库已有成熟先例可照抄**：`tools\PatchClientOnlineAwardDialogueText.py`（往 `LuaText.lua` 追加文本键）、
`tools\PatchClientNpcDialogueChineseLocale.py`、`tools\PatchClientNpcDialogueProbeTags.py`、
`tools\PatchClientLevelSealerDialogue.ps1`、`tools\PatchClientGearMentorLocalization.ps1`、
`tools\PatchClientPetGrowthResetDialog.ps1`（往 NpcFun 脚本里注入 Lua 块）。
也就是说"生成补丁 + 应用补丁"是这套代码库的既有工作方式，不是新发明。

**不打客户端补丁的退路（可选方案，值得知道）**：全服只有 3 个 opcode 能带自由文本，
**没有一个能画进 NPC 对话框**，但可以得到"服务器发的文字"：

| 方案 | 效果 | 限制 |
|---|---|---|
| `10038` type50 **channel 1**（`PacketBuilder.PythonNote.cs:150-166`，收原始字节） | 右侧个人日志里出现**中文** | 文本在日志区，不在对话框里；≤126 字节 |
| `10038` type50 channel 0 / `10169`（`PacketBuilder.ServerNote.cs:26`） | 居中公告 / 弹窗 | **仅 ASCII**；`10169` 是弹窗 |
| `10035`（`PacketBuilder.Chat.cs:29`，UTF-16） | 聊天栏，**任意 Unicode** | 是聊天，不是 NPC 窗口 |

所以"不打补丁"能做出：对话框里放**按钮**（文字用客户端现成的键）+ 把操作者写的整句中文发到日志/公告。

**未验证的一点（唯一）**：`flags = 0` 的说明窗（服务器把 `npc.NpcKey` 当脚本键发，
`GameClientHandler.NpcDialogOpen.cs` 的说明窗分支）在客户端 `NPCDescription.dat` 里**查不到该键**时，
会不会把**键名本身**当字面文本画出来。如果会，那就有一条"不补丁也能塞任意 ASCII 进一个无按钮窗口"的路子。
这需要一次游戏内点击验证，**在设计里不要依赖它**。


## ⑤ 导出 —— 能

导出三种产物，正好对应三个消费方：

| 产物 | 内容 | 用途 |
|---|---|---|
| `gm-content.json` | 标记点 / 刷怪 / 属性 / NPC / 对话树的完整快照 | 备份、换服、再导入 |
| 服务端覆盖行 | ③④ 用到的 GM 表内容（SQL 或直接是表数据） | 服务端读取生效 |
| **客户端补丁** | 生成的 `NpcFunGm.lua` + `NpcFun.lua` 插入片段 + 可选的 `NpcName.dat`/`NPCDescription.dat` 追加行 | 让④的文本/名字真的显示出来 |

## 需要你拍板的三件事

1. **④ 的文本走哪条路？**
   - (a) 只复用客户端**现成文本键**：零客户端补丁、零风险，但文字只能是客户端已有的那些句子。
   - (b) **自由文本 + 自定义 NPC 名字**：需要工具生成并应用一次客户端 Lua/数据补丁
     （仓库已有同款补丁工具链）。能力最强，但客户端更新/换服后要重打。
   - 我建议：**两者都支持**，(a) 默认，(b) 作为"生成补丁"按钮，由操作者决定何时应用。
